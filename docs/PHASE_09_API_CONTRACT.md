# Phase 09 API contract — Receipts and print documents

## Principles
- Receipt content is generated from authoritative persisted snapshots, never recomputed from today's menu/tax/company data.
- FINAL/PARTIAL_PAYMENT documents are created only after the corresponding financial transaction commits.
- Printer failure never reverses payment/refund/shift state.
- Duplicate receipt creates a new document linked to the original; it never mutates the original.
- Refund receipt is a separate financial document linked to the refund ledger entry.
- Direct Windows USB transport remains Phase 11. Phase 09 creates printer-neutral immutable documents and post-commit jobs only.

## Endpoints
- `POST /api/orders/:orderId/bill` — pre-payment customer bill snapshot.
- `GET /api/orders/:orderId/receipts` — document history.
- `POST /api/receipts/:receiptId/duplicate` — permission checked duplicate document.
- `POST /api/receipts/:receiptId/print` — enqueue post-commit 58/80mm print job.
- `POST /api/payments/:paymentId/receipt` — final or partial-payment receipt from committed payment state.
- `POST /api/refunds/:refundId/receipt` — refund receipt from committed refund state.

All mutating calls require authenticated actor identity. Receipt numbering must be generated by a concurrency-safe database sequence/counter in the implementation adapter.
